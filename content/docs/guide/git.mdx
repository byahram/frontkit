## Overview

이 문서의 브랜치 전략과 PR 기준은 **FrontKit의 기본 권장안**입니다.
저장소에서 브랜치 보호, PR 승인 규칙, 커밋 메시지 강제 설정이 확인되었다는 의미는 아닙니다.
작업 전 팀의 실제 기본 브랜치와 리뷰 규칙을 확인하세요.

## Recommended Rules

- 브랜치는 `feat/guide-content`, `fix/navigation-link`, `docs/typescript-guide`처럼 목적을 드러내도록 작성합니다.
- 한 브랜치와 PR에는 리뷰 가능한 하나의 작업 목적을 담습니다.
- Conventional Commits 형식인 `type: description`을 권장합니다.
- `feat`, `fix`, `docs`, `refactor`, `chore` 중 변경의 실제 성격에 맞는 type을 사용합니다.
- PR에는 문제·변경 결과·검증·남은 제한을 작성합니다. UI 변경은 가능하면 화면도 첨부합니다.
- 알려진 기존 검사 실패와 이번 변경의 실패를 구분해 기록합니다.

## Examples

### 작업 브랜치와 변경 확인

```bash
git status --short
git fetch origin
git switch -c docs/guide-content
# 문서를 수정한 뒤 변경 범위를 확인합니다.
git diff --stat
git diff --check
git diff -- content/docs/guide
```

`git fetch`는 원격 정보를 갱신하지만 현재 작업 브랜치를 병합하지 않습니다.
기준 브랜치에서 시작했는지는 별도로 확인하세요.

### 커밋 예시

문서 변경을 직접 검토한 후 필요한 파일만 선택합니다.

```bash
git add content/docs/guide
# staged diff를 검토합니다.
git diff --cached
git commit -m "docs: add FrontKit development guides"
```

기능 변경이라면 `feat: add Guide navigation`처럼 결과를 설명할 수 있습니다.
아래는 **제안하는 PR 본문 형식**입니다.

```markdown
## Problem

어떤 사용자의 문제를 해결하는가?

## Changes

변경 후 어떤 동작을 제공하는가?

## Validation

실행한 검사와 결과, 기존 실패와 신규 실패를 구분한다.

## Limitations

확인하지 못한 항목이나 후속 결정이 필요한 항목을 기록한다.
```

## Common Mistakes / Notes

- 리뷰하지 않은 파일까지 포함하는 `git add .` 사용을 습관화하지 않습니다.
- `.env` 값, 토큰, 로컬 비밀정보를 커밋하지 않습니다.
- 공유 브랜치의 강제 push나 `reset --hard`를 기본 작업 절차로 사용하지 않습니다.
- 이 문서의 명령은 사용 예제입니다. 실제 커밋·push·배포는 작업 권한과 팀 절차에 따라 진행합니다.
